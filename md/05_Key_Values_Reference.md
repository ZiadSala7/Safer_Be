# Quick Reference — Critical Keys That Must Be Carried Between Steps

This is the "don't lose these" cheat sheet. Each key below is produced by one step and consumed by a later one — never generated by the frontend itself.

| Key | First appears in | Must be re-sent in | Why it matters |
|---|---|---|---|
| `city_code` | Your own request (Step 1) | — | Determines which cities/suppliers get searched. |
| `supplier` | Search response (Step 1) | Rooms (Step 2), Checkout (Step 3) | Tells the backend whether to talk to TBO or Juniper for this hotel. |
| `rate_plan_code` | Search response (Step 1) | Rooms (Step 2) | Juniper needs this to fetch live room availability for that specific rate plan. |
| `room_id` | Rooms response (Step 2) | Checkout (Step 3) | Acts as the backend's price-cache key — this is what locks the price. |
| `room_code` / `room_type_code` | Rooms response (Step 2) | Checkout (Step 3) | Identifies exactly which room type was selected. |
| `total_price` | Rooms response (Step 2) | Checkout (Step 3) | The price you displayed to the user — sent back so the backend can validate/lock it. |
| `booking_reference` | Checkout response (Step 3) | Booking status lookup (Step 4) | The unique ID for tracking/confirming the booking after payment. |

**Golden rule:** if a value came back from a previous API response, pass it forward untouched — don't reconstruct, reformat, or guess it.
